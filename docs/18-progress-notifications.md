# 解包进度通知

## 用户行为

- 拖入一个或多个安装包后，在同一条系统通知中显示当前输入、当前包及处理阶段。
- 已知总量时显示百分比和实际处理大小；未知时使用不确定进度动画，不按时间模拟百分比。
- 百分比属于当前阶段，不代表整个任务或剩余时间。进入内层包会切换包名并重新计数；批量显示输入序号，不将不同大小的包等权折算成总体百分比。
- 超过 500 ms 的任务才显示进度，后续每 250 ms 最多提交一次。更新不会重新弹出横幅；可在通知中心查看。
- 完成时将同一任务的通知替换为结果，已有进度时不再弹出单独的完成横幅。短任务只显示一条包含包名的结果通知。
- 单包结果包含包名及输出位置或失败原因；批量结果包含包名和各状态数量。用户关闭进度后停止更新，结束时结果静默保存在通知中心。失败或部分完成不显示“全部成功”。
- `--quiet` 和 `--list` 不发送进度通知。通知不可用、被禁用或更新失败，不影响文件提取。

## 数据来源

| 阶段 | 计量方式 |
| :--- | :--- |
| 格式识别、目录解析、内层扫描、结果整理 | 不确定进度 |
| 当前包提取 | 实际成功写入的载荷字节 / 文件清单中的本层总大小；不累计日志、报告或缓存 |
| SHA 文件校验、安装包 CRC-32 | 实际已校验字节 / 待校验数据大小 |
| MSI 内嵌 CAB 准备 | 已读取并缓存的字节；总量未知 |
| NSIS Solid 解码、压缩文件大小测量 | 解码器实际读取的压缩字节 / 该压缩流大小，文字明确注明计量含义 |
| Inno 数据块跳过区域 | 实际解码的跳过字节 / 待跳过区域大小 |
| 7z 数据块解码 | 现有 SDK 一次性解码块，不提供输出进度回调，使用不确定进度；后续写文件时恢复本层字节进度 |

文件计数不用于估算百分比，避免一个大文件和一个小文件等权。文件校验和缓存解码不会累加到文件提取的计数中。零字节或不可靠的总量不计算比例；计数超过声明总量时退回不确定进度，实际数据校验仍由解析器处理。

## 实现

`core/progress.*` 通过线程局部连接绑定观察器，阶段使用栈式作用域，子阶段结束后恢复父阶段。快照采用固定容量文本，避免进度上报增加解包的内存分配失败点。回调异常、重入和系统错误码均被隔离。

写入载荷使用 `platform::write_payload`，每次成功的 Win32 写入才递增进度。报告和缓存继续使用不计入提取量的 `write_all`。树形提取在每个包创建独立的文件总量，最终结果沿用原有文件校验、目录提交和任务摘要流程。

通知使用 Windows 自带的 WinRT ABI：`ToastGeneric`、`progress`、`NotificationData` 和 `IToastNotifier2::UpdateWithTagAndGroup`，无需 Windows App SDK 或外部运行库。每个任务用任务 ID 分组，递增序号防止旧更新覆盖新值。Windows 10 1703 以前缺少更新接口时仅保留结果通知。

参考：[微软进度通知与数据绑定说明](https://learn.microsoft.com/zh-cn/windows/apps/design/shell/tiles-and-notifications/toast-progress-bar)。

## 验证

`progress_integration` 使用惰性 ZIP/CAB 数据，验证大文件内部持续上报、Unicode 路径、SHA 校验阶段、内层包总量隔离、损坏文件回滚以及观察器异常不影响提取。探针还验证线程隔离、重入抑制、错误码保留、计数溢出和 Unicode 文本截断。

完整格式回归仍通过原有提取和摘要测试验证。系统通知横幅受用户设置和免打扰影响，通知 API 成功不等于已完成所有 Windows 版本的视觉验收。

在已登录的 Windows 桌面会话中，可用 Windows PowerShell 5.1 运行本机通知测试：

```powershell
powershell.exe -NoProfile -File tests/notification_progress.ps1 `
  -Executable out/dist/win-x64-release/Extract.exe `
  -WorkRoot out/notification-validation -Mode normal
```

`-Mode` 支持 `normal`、`dismiss`、`quiet`、`short`、`failure` 和 `batch`。脚本生成惰性 ZIP，运行 Extract，并读取该任务的通知历史和更新日志；长任务样本展开后占用 1 GiB。它验证原生更新返回成功、最终只保留一条含包名的结果、关闭后停止更新，以及静默和批量行为。证据保存为 `notification-validation.json`；此测试需要交互桌面，不纳入无桌面环境的 CTest。
