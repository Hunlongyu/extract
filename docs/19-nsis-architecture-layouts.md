# NSIS 架构分支目录

## 问题与结果

部分 NSIS 安装包在两个条件分支中分别存放 x86、x64 的同名程序与依赖。此前所有不同内容的同名文件都各自进入 `_variants/file-…/app/`，共用文件则留在 `app`。载荷没有丢失，但主程序、依赖和资源分散，用户无法直接选用完整目录。

对于已确认的双分支架构布局，现在分别输出 `app-x64`、`app-x86` 或 `app-arm64`。两分支各自的普通资源保留在对应目录；分支外的应用文件及两个分支引用的同一载荷分别保存到两套目录。`plugins`、`temp` 等逻辑根保持原有结构。输出体积和进度总量按实际保存的文件计数。

## 静态判断边界

- 只处理具有明确合流点的两个直线条件分支，不执行判断或脚本。
- 两个分支内部只允许当前识别的文件、目录、属性、变量赋值及提示指令；出现嵌套跳转、函数或插件调用时保持原有布局。
- 检查区段及外部跳转入口。存在间接目标或外部进入分支内部时不归组。
- 在同目标、不同载荷的 PE 文件中读取 Machine 和可选头魔数，要求至少一对不同架构且各对证据一致。仅读取前 4 KiB，无法确认时不猜架构。
- 分支归属决定文件归属。两版本的翻译资源可能都是 x86 PE，共用辅助程序也可能是 x86，不能把所有文件按自身 Machine 拆分。
- 归组会保留原始目标路径、来源表达式和指令编号，新增稳定架构后缀以区分复制的条目。
- 存在同分支内容冲突、文件与目录前缀冲突、架构证据矛盾，或分析达到工作量预算时，保持原有 `_variants` 防覆盖处理。

该功能整理静态文件布局，不恢复安装器执行后生成的文件、注册表、服务或其他系统状态，也不保证提取的软件无需安装即可运行。

## 验证

`tests/nsis_integration.py` 使用官方 NSIS 编译器生成惰性包，覆盖普通/固实 LZMA、x64/x86 与 ARM64/x86 布局、共用文件、不同内容的同架构资源、单分支独有文件和子目录依赖；逐文件核对内容、大小、SHA-256 和报告总量。相同架构候选、嵌套条件、外部跳入、共用路径冲突及架构矛盾均验证保守回退。没有执行任何测试载荷，ARM64 载荷只是静态格式测试数据。

本次 x86、x64 的 NSIS 回归各完成 108 次 Extract 调用，均通过；路径安全与真实进度测试均通过，嵌套提取回归也通过。两种 Release 的静态 CRT 和单文件依赖检查通过。

用户提供的 Beyond Compare 5.2.5.32528 包为 NSIS Unicode、LZMA Solid，输入 SHA-256：

```text
b0f2ea898b985af0b30b0a37b4d533b62af3cf3615f1a6e2857d258363152f44
```

修复后 x64 目录 19 个文件，x86 目录 17 个文件，安装器插件目录 19 个文件。两套应用目录与独立读取 NSIS 数据流及 File 指令获得的载荷逐字节一致；55 个输出文件均核对提取后 SHA-256。安装器和提取后的程序均未执行。
